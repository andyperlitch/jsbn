Why the original 800-iter ranking lied

big-integer is a native BigInt wrapper in this engine, so it was never a like-for-like JS big-integer implementation. jsbn’s public arithmetic now uses the same engine primitive and only materializes the classic 28-bit digit array when something like toByteArray needs it — which is why add and multiply land within a few percent of big-integer, while gcd and modPow pull ahead (Euclid and windowed exp on raw BigInt, versus their method-call loops). bn.js still wins nothing here: it is a JS limb library. bignumber.js is a general decimal library, fast-ish at toString until you cache the decimal from parse, and slow at integer multiply and divide.
